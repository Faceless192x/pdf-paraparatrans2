# ParaParaTrans 機能分析・開発方向性の検討

本ドキュメントは、ユーザー視点での今後の開発方向性を、競合ツールとの比較や市場ニーズの分析を踏まえて検討したものです。

---

## 1. ParaParaTrans の現在の強み

### 1.1 他ツールにない独自の価値

| 強み | 詳細 |
|------|------|
| **段落単位の翻訳管理** | PDF から段落を抽出し、1 段落ずつステータス管理（未翻訳→自動→下書き→確定）できるツールは他にほぼ存在しない。Adobe や DeepL の PDF 翻訳は「丸ごと翻訳」のみで、段落レベルの推敲ワークフローを持たない |
| **ローカル動作・プライバシー** | データがローカルに保存され、クラウドに依存しない。翻訳 API 呼び出し以外のデータ送信がなく、NDA 文書や未公開コンテンツの翻訳に安心して使える |
| **無料・オープンソース** | 商用 CAT ツール（Trados: 数万円、memoQ: 数万円）と同等以上のワークフローを無料で提供。OmegaT は無料だが PDF 段落抽出は弱い |
| **PDF 原文と翻訳テキストの並列表示** | PDF ビューアと段落テキストを左右に並べて表示。原文レイアウトを確認しながら翻訳できる UI は類似ツールにない |
| **辞書による用語統一** | グローバル辞書＋文書別辞書による事前置換。翻訳前に用語を統一し、API 翻訳の品質を底上げする仕組み |
| **シンボルフォント対応** | Wingdings や独自フォント（RuneQuest 等の TTRPG ルールブックで頻出）の文字を読み取り可能なテキストに置換する機能 |
| **URL ブック** | Web ページを PDF と同じワークフローで翻訳できるユニークな機能 |

### 1.2 ターゲットユーザー像

- **TTRPG ルールブック翻訳者**: 英語 PDF を日本語に翻訳する個人・サークル。特殊フォント対応、用語辞書、段落単位推敲のすべてが刺さる
- **技術文書翻訳者**: マニュアル・仕様書の翻訳で、用語統一と段落管理が必要なユーザー
- **個人翻訳者・学習者**: 無料で PDF 翻訳ワークフローを使いたいユーザー
- **機密文書を扱うユーザー**: ローカル動作が必須の企業・組織

## 2. 競合ツールとの比較

### 2.1 PDF 翻訳ツール（丸ごと翻訳型）

| ツール | 特徴 | ParaParaTrans との違い |
|--------|------|----------------------|
| **DeepL PDF翻訳** | 高品質な翻訳、レイアウト保持 | 段落単位の編集不可、用語辞書は限定的、無料版はサイズ制限あり |
| **Adobe Acrobat AI翻訳** | レイアウト保持が最高水準 | 有料、段落単位の推敲ワークフローなし |
| **Google Translate** | 249言語対応、無料 | レイアウト崩壊が多い、編集不可 |
| **DocTranslator** | 大容量対応、フォーマット保持 | 有料（従量制）、段落管理なし |

**ParaParaTrans の優位点**: 「翻訳して終わり」ではなく「翻訳してから推敲する」ワークフロー全体をサポート。

### 2.2 CAT ツール（翻訳支援ツール）

| ツール | 特徴 | ParaParaTrans との違い |
|--------|------|----------------------|
| **Trados Studio** | 業界標準、TM・用語管理・QA | 高価（数万円）、学習コスト高、PDF 抽出は限定的 |
| **memoQ** | チーム翻訳向け、TM 共有 | 高価、Windows 専用 |
| **Phrase (Memsource)** | クラウドネイティブ、AI 統合 | サブスクリプション、データがクラウドに保存 |
| **OmegaT** | 無料・オープンソース、TM 対応 | PDF 抽出が弱い、UI が古い |

**ParaParaTrans の優位点**: PDF 段落抽出の精度が高く、セットアップが簡単。CAT ツールが持つ翻訳メモリ機能は未搭載だが、辞書機能で用語統一をカバー。

### 2.3 LLM ベース翻訳ツール

| ツール | 特徴 | ParaParaTrans との違い |
|--------|------|----------------------|
| **ChatGPT / Claude 直接利用** | 文脈理解力が高い、日英翻訳で最高品質 | PDF の段落抽出・管理機能なし、手動コピペが必要 |
| **Linnk AI PDF Translator** | LLM 連携、並列表示 | 段落ステータス管理なし |
| **AiNiee** | ゲーム翻訳特化、複数 LLM 対応 | PDF 翻訳ではない（ゲームファイル向け） |

**ParaParaTrans の優位点**: PDF 段落抽出＋翻訳管理ワークフローは唯一無二。LLM 翻訳エンジンを追加すれば、最高品質の翻訳＋段落管理の両方を実現できる。

## 3. 開発方向性の提案

### 3.1 優先度：高 — LLM 翻訳エンジンの追加

**背景**: 2025年の翻訳品質ベンチマーク（WMT24）で、Claude 3.5 が日英翻訳で最高評価を獲得。GPT-4 もDeepL を上回る品質を示している。LLM 翻訳は特にニュアンス・文脈・トーンの再現で従来 API を大きく凌駕する。

**提案内容**:
- OpenAI API（GPT-4 / GPT-4o）対応の翻訳エンジンモジュール追加
- Anthropic API（Claude）対応
- Google Gemini API 対応
- 翻訳エンジン選択 UI での切り替え（既存の Google / DeepL と同様）

**実装方針**:
- 既存の `modules/api_translate_google.py` と同じインターフェースで `modules/api_translate_openai.py`、`modules/api_translate_anthropic.py` を追加
- `.env` に `OPENAI_API_KEY`、`ANTHROPIC_API_KEY` を追加
- LLM ではプロンプトで翻訳コンテキスト（前後の段落、辞書用語）を渡せるため、従来 API より高品質な翻訳が期待できる

**ユーザーへのインパクト**: 翻訳品質の大幅向上。特に日英翻訳での自然さ・正確性が向上し、推敲作業が軽減される。

---

### 3.2 優先度：高 — 翻訳メモリ（TM）機能

**背景**: CAT ツールの最大の強みは翻訳メモリ。過去に翻訳した文を蓄積し、類似文の翻訳を自動提案する。特に同じシリーズの TTRPG ルールブックや技術文書では、繰り返し表現が多く効果が大きい。

**提案内容**:
- 翻訳確定済みの段落（原文＋訳文ペア）を翻訳メモリとして蓄積
- 新規段落翻訳時に、過去の類似文を検索・提案
- TMX 形式でのエクスポート/インポート（業界標準フォーマット）

**実装方針**:
- JSON ベースのローカル TM ストア（既存のデータ構造と親和性が高い）
- 類似度検索は簡易的な文字列マッチング（Levenshtein 距離等）から開始
- 将来的に Embedding ベースのセマンティック検索に拡張可能

**ユーザーへのインパクト**: シリーズ物の翻訳作業が劇的に効率化。商用 CAT ツールの主要機能を無料で提供。

---

### 3.3 優先度：中 — LLM を活用した翻訳支援機能

**背景**: LLM は単なる翻訳だけでなく、翻訳の推敲・校正・用語提案にも活用できる。

**提案内容**:
- **翻訳レビュー支援**: 翻訳済みテキストを LLM に評価させ、改善提案を表示
- **用語辞書の自動生成**: 文書から専門用語を自動抽出し、辞書候補を提案
- **文脈を考慮した翻訳**: 前後の段落やドキュメント全体のコンテキストを LLM に渡して翻訳精度を向上
- **代替訳の提示**: 1つの段落に対して複数の翻訳候補を提示し、ユーザーが選択

**ユーザーへのインパクト**: 推敲作業の質が向上。特に翻訳初心者にとって、LLM による改善提案は学習効果もある。

---

### 3.4 優先度：中 — OCR 対応（スキャン PDF）

**背景**: 古い TTRPG ルールブックや紙の文書をスキャンした PDF はテキスト抽出ができない。Tesseract OCR（無料・オープンソース）の統合で対応可能。

**提案内容**:
- Tesseract OCR エンジンの統合
- スキャン PDF の自動検出と OCR 処理
- OCR 結果の手動修正 UI

**ユーザーへのインパクト**: 対応可能な PDF の範囲が大幅に拡大。古い文書やスキャン文書の翻訳ニーズに応える。

---

### 3.5 優先度：中 — エクスポート・出力の強化

**背景**: 現在は HTML・マークダウン・テキスト出力に対応しているが、翻訳済み PDF やバイリンガル PDF の需要が高い。

**提案内容**:
- **翻訳済み PDF 出力**: 原文 PDF のレイアウトを保持しつつ、テキストを翻訳文に差し替えた PDF を生成
- **バイリンガル PDF**: 原文と訳文を見開きで並べた PDF を出力
- **DOCX 出力**: Word 形式での出力（編集・共有の容易さ）
- **XLIFF 出力**: 翻訳業界標準フォーマットで、他の CAT ツールとの互換性を確保

**ユーザーへのインパクト**: 翻訳成果物の共有・配布が容易になる。特に翻訳済み PDF は最終納品物として需要が高い。

---

### 3.6 優先度：低 — 協調翻訳機能

**背景**: 大型ルールブック（数百ページ）の翻訳プロジェクトでは複数人での分担翻訳が一般的。

**提案内容**:
- ページ範囲ごとの担当者割り当て
- 翻訳進捗のダッシュボード
- 構造エクスポート/インポートの改善 (現在も JSON 構造エクスポートで部分対応)
- コメント・メモ機能

**ユーザーへのインパクト**: チーム翻訳プロジェクトでの利用が可能になる。ただし、ローカルアプリの性質上、本格的なリアルタイム協調は難しく、非同期型の協調に焦点を当てる。

---

### 3.7 優先度：低 — UI/UX の改善

**提案内容**:
- **翻訳進捗の可視化**: ステータス別の段落数・進捗率を表示するプログレスバー
- **一括操作の強化**: 複数段落の一括ステータス変更、一括タグ付け
- **ダークモード**: 長時間作業のユーザー向け
- **モバイル対応**: レスポンシブデザインによるタブレットでの閲覧
- **翻訳比較モード**: 同じ段落の Google / DeepL / LLM 翻訳を並べて比較

**ユーザーへのインパクト**: 日常的な使い勝手の向上。特に翻訳比較モードは、どのエンジンが最適かをユーザーが判断する助けになる。

## 4. 市場ニーズと戦略的ポジショニング

### 4.1 ParaParaTrans が狙うべきポジション

```
                    高品質翻訳
                        ↑
                        |
        CAT ツール      |     LLM 直接利用
        (Trados/memoQ)  |     (ChatGPT/Claude)
                        |
  翻訳管理 ←————————————+————————————→ 手軽さ
  ワークフロー          |
                        |
     ParaParaTrans ★    |     DeepL/Google
     (ここを目指す)     |     PDF翻訳
                        |
                    低コスト
```

**戦略**: 「無料で使える、段落レベルの PDF 翻訳ワークフローツール」というユニークなポジションを維持しつつ、LLM 統合で翻訳品質を CAT ツール＋プロ翻訳者レベルに引き上げる。

### 4.2 差別化の3本柱

1. **PDF 段落抽出の精度**: 他ツールが苦手とする複雑なレイアウトの PDF（2段組、ヘッダー/フッター、特殊フォント）に対応
2. **翻訳ワークフロー管理**: ステータス管理＋辞書＋TM で、翻訳プロセス全体をカバー
3. **ローカル＋オープンソース**: プライバシーとコスト面での優位性

### 4.3 成長が見込まれるニーズ

| ニーズ | 背景 | ParaParaTrans の対応状況 |
|--------|------|------------------------|
| LLM 翻訳の品質活用 | Claude/GPT-4 が翻訳ベンチマークで従来 API を凌駕 | ❌ 未対応 → **最優先で対応すべき** |
| ローカル AI 翻訳 | プライバシー重視の企業需要増加。Ollama 等のローカル LLM の普及 | 部分対応（ローカル動作だが翻訳は API 依存） |
| TTRPG 翻訳の需要増 | 海外 TTRPG の日本語翻訳需要が増加（D&D、Pathfinder 等） | ✅ 強み（シンボルフォント対応等） |
| 翻訳成果物の共有 | 翻訳コミュニティでの成果物共有ニーズ | △ 構造エクスポートで一部対応 |
| ブラウザ拡張連携 | Web ページの翻訳ニーズ | ✅ Chrome 拡張＋URL ブックで対応済み |

## 5. ユーザー拡大のための施策

ユーザー数を広げるにあたっての主要な課題は **セットアップの複雑さ**（特に翻訳 API キーの取得）と **ローカル環境への依存** である。ここでは、サーバーを自前で用意せず、著作権にも配慮した形でのアプローチを検討する。

### 5.1 セットアップの簡素化

#### 5.1.1 現状の課題

現在のセットアップには以下のハードルがある:

| ステップ | 難易度 | 離脱リスク |
|----------|--------|-----------|
| Python インストール | 中 | 非技術者にとってハードル |
| pip install | 低 | コマンドライン操作が必要 |
| Google Cloud コンソールでの API キー取得 | **高** | GCP プロジェクト作成、API 有効化、キー制限設定が煩雑 |
| DeepL API キー取得 | 中 | アカウント作成＋認証キー取得 |
| .env ファイル作成・編集 | 中 | テキスト編集の知識が必要 |

**最大のボトルネック**: 翻訳 API キーの取得。特に Google Cloud は「プロジェクト作成→API 有効化→認証情報作成→キー制限」の多段階手順で、非エンジニアの離脱率が高い。

#### 5.1.2 API キー不要の翻訳エンジン — Ollama（ローカル LLM）

**最も有望なアプローチ**: API キー自体を不要にする。

Ollama はローカルで LLM を動かすオープンソースツールで、2025年現在急速に普及している。翻訳エンジンとして統合すれば:

- ✅ **API キー不要** — インストールするだけで翻訳可能
- ✅ **完全オフライン動作** — インターネット接続不要（モデルダウンロード後）
- ✅ **完全無料** — API 課金なし
- ✅ **プライバシー最強** — データが一切外部に送信されない
- ✅ **翻訳品質が向上中** — Llama 3、Gemma、Mistral 等のモデルが多言語翻訳で実用レベルに到達

**実装方針**:
- `modules/api_translate_ollama.py` を追加
- Ollama の REST API（`http://localhost:11434/api/generate`）を呼び出し
- `.env` には `TRANSLATOR=ollama` と `OLLAMA_MODEL=gemma3:12b` 等を設定
- Ollama が起動していない場合のエラーメッセージとセットアップガイドを表示

**セットアップ手順（ユーザー視点）**:
1. Ollama をインストール（[ollama.com](https://ollama.com) からワンクリック）
2. `ollama pull gemma3:12b`（翻訳用モデルを 1 コマンドでダウンロード）
3. ParaParaTrans の `.env` に `TRANSLATOR=ollama` を設定
4. 完了 — API キー取得ステップが完全に消える

**ハードウェア要件**: 8GB 以上の RAM（16GB 推奨）。GPU があれば高速だが CPU でも動作。

#### 5.1.3 クレジットカード不要の翻訳 API

API キーは必要だが、クレジットカード不要で始められる選択肢:

| サービス | 無料枠 | カード不要 | 特徴 |
|----------|--------|-----------|------|
| **LibreTranslate** | 無制限（セルフホスト） | ✅ | オープンソース、ローカル実行可能 |
| **DeepL API Free** | 50万文字/月 | ❌（要カード） | 高品質だがカード必要 |
| **Google Cloud** | $300 クレジット（90日） | ❌（要カード） | トライアル後は課金 |

**提案**: LibreTranslate のローカルインスタンスを翻訳エンジンとして統合。Ollama と同様に API キー不要で動作。

#### 5.1.4 初回起動ウィザード

**提案**: アプリ初回起動時にブラウザ上でセットアップウィザードを表示。

1. **翻訳エンジン選択画面**: 各エンジンの特徴を比較表で表示
   - Ollama（API キー不要・オフライン）
   - Google Translate（手軽・安価）
   - DeepL（高品質）
2. **選択したエンジンのセットアップガイド**: スクリーンショット付きの手順を表示
3. **API キーの入力**: `.env` ファイルの直接編集ではなく、ブラウザ画面から入力
4. **接続テスト**: 「テスト翻訳」ボタンで設定が正しいか確認
5. **完了**: 自動的に設定ファイルに保存

**ユーザーへのインパクト**: `.env` ファイルの手動編集が不要になり、非エンジニアでもセットアップ可能に。

### 5.2 ローカル以外での動作環境

自前サーバーを用意せずに、ローカル以外で ParaParaTrans を動かす方法を検討する。

#### 5.2.1 GitHub Codespaces（既存・強化）

現在すでに Codespaces 対応しているが、以下の強化が考えられる:

| 強化案 | 詳細 |
|--------|------|
| **ワンクリック起動ボタン** | README に「Open in Codespaces」バッジを追加。リンクをクリックするだけで環境が立ち上がる |
| **Secrets の自動プロンプト** | Codespace 起動時に API キー未設定を検出し、設定画面を自動表示 |
| **データ永続化ガイド強化** | Codespace 削除時のデータ消失リスクに対する自動バックアップスクリプト |
| **コスト管理ガイド** | 無料枠（月120コア時間）の範囲での使い方ガイド |

**Codespaces の制約**: 月120コア時間（2コアで約60時間）の無料枠。個人利用には十分だが、常時稼働は不可。

#### 5.2.2 Gitpod 対応

Codespaces と類似のクラウド開発環境。追加のユーザー層にリーチできる:

- 月50時間の無料枠（Codespaces より少ないが別アカウント）
- `.gitpod.yml` の追加で対応可能（`.devcontainer` と類似）
- GitHub アカウント不要（GitLab、Bitbucket でも利用可能）

#### 5.2.3 Google Colab + ngrok パターン

技術者向けだが、完全無料でクラウド上に ParaParaTrans を立てる方法:

1. Google Colab ノートブックを用意
2. ParaParaTrans をインストール・起動
3. ngrok でインターネットからアクセス可能にする
4. 生成された URL をブラウザで開く

**制約**: Colab セッションは最大12時間で切断。データの永続化には Google Drive マウントが必要。

#### 5.2.4 Docker イメージ配布

Docker 対応により、環境構築を完全に自動化:

- `Dockerfile` と `docker-compose.yml` を提供
- `docker-compose up` だけで起動
- NAS（Synology、QNAP 等）での常時稼働も可能
- Ollama コンテナとの連携で翻訳エンジンも含めたオールインワン構成

```yaml
# docker-compose.yml（構想）
services:
  paraparatrans:
    build: .
```

### 5.3 Git ベースの協調翻訳ワークフロー

#### 5.3.1 背景と課題

大型 PDF（数百ページの TTRPG ルールブック等）の翻訳は複数人で分担するのが一般的だが、以下の課題がある:

- **著作権問題**: 原文 PDF を複数人で共有すると著作権侵害のリスク。各翻訳者が自分で原書を購入している前提が必要
- **サーバー不要**: プロジェクトオーナーが Web サーバーを用意・維持するのは負担が大きい
- **翻訳データの統合**: 複数人の翻訳結果をマージする仕組みが必要

#### 5.3.2 提案: プライベートリポジトリ＋プルリクエスト型協調翻訳

GitHub のプライベートリポジトリと既存の構造エクスポート機能を組み合わせた、著作権に配慮した協調翻訳モデル:

**前提**:
- 各翻訳者が原書の PDF を自分で所有している
- 翻訳プロジェクトの管理者が GitHub プライベートリポジトリを作成
- 原文テキスト（`src_text` 等）はリポジトリに含めない（著作権保護）

**ワークフロー**:

```
┌─────────────────────────────────────────────────┐
│  プロジェクト管理者                                │
│                                                   │
│  1. PDF を ParaParaTrans で段落抽出                │
│  2. 構造データ（タグ・順序・結合情報）をエクスポート│
│  3. プライベート GitHub リポジトリに push            │
│     ※ 原文テキストは含まない（著作権保護）          │
│  4. 翻訳担当ページ範囲を Issue で割り当て           │
└──────────────┬──────────────────────────────────┘
               │
    ┌──────────▼──────────┐
    │   翻訳者 A〜N        │
    │                      │
    │  1. リポジトリを fork │
    │  2. 自分の PDF から   │
    │     ParaParaTrans で │
    │     段落抽出          │
    │  3. 構造データを      │
    │     インポート        │
    │  4. 担当ページを翻訳  │
    │  5. 翻訳テキストだけ  │
    │     をエクスポート    │
    │  6. PR を作成         │
    └──────────┬───────────┘
               │
    ┌──────────▼──────────┐
    │   レビュー・マージ   │
    │                      │
    │  - PR 上で翻訳レビュー│
    │  - GitHub の差分表示  │
    │    で変更を確認       │
    │  - 承認後マージ       │
    │  - 辞書ファイルも     │
    │    同様にPRで管理     │
    └──────────────────────┘
```

**リポジトリに含めるもの（著作権セーフ）**:

| ファイル | 内容 | 著作権 |
|----------|------|--------|
| `structure.json` | 段落の順序・タグ・結合情報 | ✅ セーフ（構造データのみ） |
| `translations.json` | 翻訳テキスト（訳文のみ） | ✅ セーフ（翻訳者の著作物） |
| `dict.txt` | 用語辞書 | ✅ セーフ（用語対応表） |
| `progress.md` | 翻訳進捗 | ✅ セーフ |

**リポジトリに含めないもの（著作権リスク）**:

| ファイル | 内容 | 理由 |
|----------|------|------|
| `*.pdf` | 原書 PDF | ❌ 著作権侵害 |
| `src_text`、`src_html` | 原文テキスト | ❌ 著作物の複製 |

#### 5.3.3 必要な機能拡張

この協調翻訳モデルを実現するために必要な機能:

1. **翻訳テキストのみのエクスポート/インポート**
   - 既存の構造エクスポートは原文を除外するが、翻訳テキストも除外してしまう
   - 「翻訳テキストのみ」のエクスポート形式を追加
   - 段落 ID をキーにして、翻訳テキストだけをマージできるインポート機能

2. **ページ範囲指定のエクスポート**
   - 翻訳者が担当ページのデータだけをエクスポート/インポートできる機能
   - 担当範囲外のデータを誤って上書きしない安全機能

3. **差分検出・コンフリクト解決**
   - 同一段落を複数人が翻訳した場合の競合検出
   - 翻訳テキストの差分表示と選択 UI

4. **GitHub Actions による自動チェック**（将来構想）
   - PR 作成時に翻訳カバレッジ（翻訳済み段落数/全段落数）を自動算出
   - 辞書との整合性チェック（登録用語が翻訳に使用されているか）
   - 翻訳テキストのフォーマットチェック

### 5.4 ユーザーニーズに基づく追加構想

#### 5.4.1 翻訳プロジェクトテンプレート

**ニーズ**: TTRPG 翻訳サークルが新しいルールブックの翻訳を始める際、プロジェクトのセットアップを効率化したい。

**提案**: GitHub テンプレートリポジトリとして「翻訳プロジェクトスターターキット」を提供。

含まれるもの:
- `.github/ISSUE_TEMPLATE/`: 翻訳タスクの Issue テンプレート（ページ範囲、担当者、期限）
- `CONTRIBUTING.md`: 翻訳ルール（文体統一、用語辞書の使い方、PR の出し方）
- `dict.txt`: 初期辞書テンプレート（TTRPG 共通用語の日英対応表）
- `.github/workflows/`: 翻訳カバレッジの自動レポート
- `progress.md`: 翻訳進捗テンプレート

**ユーザーへのインパクト**: 翻訳プロジェクト開始の敷居が大幅に下がり、初めてのチームでも統一されたワークフローで作業を始められる。

#### 5.4.2 翻訳コミュニティ辞書の共有

**ニーズ**: TTRPG の専門用語（D&D、Pathfinder 等のシステム共通用語）は多くの翻訳プロジェクトで共通して使われる。個々のプロジェクトで一から辞書を作るのは非効率。

**提案**:
- **公開辞書リポジトリ**: TTRPG システムごとの用語辞書をオープンソースで管理
  - `dicts/dnd5e.txt`: D&D 5e 用語辞書
  - `dicts/pathfinder2e.txt`: Pathfinder 2e 用語辞書
  - `dicts/call-of-cthulhu.txt`: CoC 用語辞書
  - `dicts/general-ttrpg.txt`: TTRPG 共通用語
- **ParaParaTrans からの辞書インポート機能**: URL を指定してリモート辞書をダウンロード・マージ
- **辞書への PR 投稿**: 翻訳作業中に発見した新用語を辞書リポジトリに PR として提案

**著作権の考慮**: 用語の対応表（「Armor Class」→「アーマークラス」等）は著作権の対象外であり、自由に共有可能。

#### 5.4.3 読書会・学習用途への展開

**ニーズ**: 英語の技術文書や論文を日本語で読みたい個人・勉強会グループ。

**提案**: 「読書モード」の追加。
- 翻訳管理ワークフロー（ステータス管理等）を簡略化した読書向け UI
- ワンクリック全文翻訳＋ページめくり型の閲覧 UI
- 用語辞書による注釈表示（原語を括弧内に表示）
- PDF と翻訳テキストの同期スクロール

**ユーザーへのインパクト**: 翻訳者だけでなく、英語文書の「読者」にもツールの利用範囲が広がる。PDF 翻訳の日常的なユースケースをカバー。

#### 5.4.4 翻訳品質スコアリング

**ニーズ**: 翻訳の完成度を客観的に把握したい。特にチーム翻訳では品質のばらつきが課題。

**提案**:
- **翻訳カバレッジダッシュボード**: ページ別・章別の翻訳進捗率
- **未翻訳用語検出**: 辞書に登録された用語が翻訳文に反映されているかチェック
- **一貫性チェック**: 同じ原文が異なる訳文になっている箇所を検出
- **LLM 品質レビュー**: 翻訳テキストを LLM に評価させ、改善が必要な段落をハイライト

#### 5.4.5 オフライン完結型パッケージ

**ニーズ**: インターネット接続が制限される環境（企業内ネットワーク、出張先等）でも使いたい。

**提案**: ParaParaTrans + Ollama を同梱したオフライン完結パッケージ。

- Windows: `pdf-paraparatrans-offline.exe`（Ollama + 軽量モデル同梱）
- Docker: `docker-compose up` で ParaParaTrans + Ollama が一括起動
- 翻訳品質は API サービスに劣るが、セットアップとプライバシーの面で最も優れた選択肢

#### 5.4.6 多言語展開

**ニーズ**: 英日翻訳以外にも、英→中、英→韓、日→英など他の言語ペアでの利用。

**提案**:
- UI の多言語化（i18n 対応）
- 翻訳方向（ソース言語・ターゲット言語）の設定 UI
- 各言語ペアに最適な翻訳エンジンの推奨表示
- README・セットアップガイドの英語版作成（海外ユーザーへのリーチ）

**ユーザーへのインパクト**: ターゲット市場が日本語圏から全世界に拡大。特に英語版 README は GitHub での発見可能性を大幅に高める。

## 7. まとめ

ParaParaTrans は「PDF 段落単位の翻訳ワークフロー管理」という、他のツールがカバーしていないニッチを確実に占めている。この強みを維持しつつ、**ユーザー拡大** のために最も効果が高い施策は以下の 3 つである。

### 施策 1: セットアップの抜本的簡素化

**Ollama（ローカル LLM）対応** により、翻訳 API キーの取得という最大のハードルを撤去する。「Ollama をインストール → ParaParaTrans を起動」の 2 ステップで翻訳作業を開始できる状態を目指す。さらに **初回セットアップウィザード** で `.env` 手動編集も不要にする。

### 施策 2: Git ベースの協調翻訳

**プライベートリポジトリ＋プルリクエスト** モデルにより、サーバー不要で著作権に配慮した協調翻訳を実現する。既存の構造エクスポート機能を拡張し、翻訳テキストのみのエクスポート/インポートを追加することで、原文テキストを共有せずにチーム翻訳が可能になる。

### 施策 3: コミュニティ資産の構築

**翻訳プロジェクトテンプレート** と **コミュニティ辞書** により、ツール単体ではなくエコシステムとしての価値を創出する。特に TTRPG 翻訳コミュニティでは、共通用語辞書の共有が大きな効率化をもたらす。

これらの施策により、ParaParaTrans は:
- **セットアップの手軽さ** で、技術的背景を持たないユーザーにもリーチし
- **Git 協調翻訳** で、チーム翻訳プロジェクトのインフラとなり
- **コミュニティ辞書** で、翻訳者コミュニティのハブとなる

という、ツールからプラットフォームへの進化を遂げることができる。
